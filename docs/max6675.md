# Sonda de temperatura MAX6675

Termopar tipo K com módulo MAX6675 na Heltec WiFi LoRa 32 V2. A montagem e as leituras ainda precisam de validação física.

## Ligações

| MAX6675 | ESP32 | Jumper |
| --- | --- | --- |
| SO | GPIO 39 (entrada) | Cinza |
| CS | GPIO 23 | Branco |
| SCK | GPIO 13 | Azul |
| VCC | 3V3 | Verde |
| GND | GND comum | Preto |

DHT22 permanece no GPIO 17 e SW-420 no GPIO 22. Todos usam alimentação em 3,3 V e terra comum.

## Firmware e upload

1. Na Arduino IDE, instale **MAX6675 library**, da **Adafruit**, pelo gerenciador de bibliotecas. Mantenha DHT sensor library, Adafruit Unified Sensor e ArduinoJson 7.x.
2. Abra `firmware/ms_monitor/ms_monitor.ino`. Preserve seu `config.h` com as configurações locais de Wi-Fi e API.
3. Selecione **Heltec WiFi LoRa 32(V2)** com o core ESP32 **3.3.12**, escolha a porta da placa, compile e faça Upload.
4. Abra o Monitor Serial em **115200 baud**. A sonda aparece como `Probe: ... C` ou `MAX6675: read failure`; HTTP 201 indica leitura aceita pela API.

A biblioteca usa comunicação por software e construtor na ordem SCK, CS, SO. A primeira leitura ocorre após a janela inicial de 2,5 s, acima do tempo máximo de conversão de 220 ms; as seguintes usam o mesmo ciclo. Falha da sonda não impede DHT22 ou vibração, e falha do DHT22 não impede a sonda. A configuração de rede e a contagem de vibração são preservadas.

## Contrato e interface

`POST /api/readings` mantém HTTP 201. `GET /api/readings/latest` mantém o envelope existente. Exemplo **simulado**, sem representar uma medição física:

```json
{
  "device_id": "simulated-probe-test",
  "uptime_ms": 125000,
  "window_ms": 2500,
  "temperature_c": 24.8,
  "humidity_pct": 59.2,
  "dht_ok": true,
  "vibration_do": 0,
  "vibration_transitions": 12,
  "probe_temperature_c": 25.25,
  "probe_ok": true
}
```

`temperature_c` é a temperatura **do ar** pelo DHT22; `probe_temperature_c` é a temperatura **no ponto da sonda**. A sonda aceita números finitos entre 0 e 1024 °C, sem aplicar os limites do DHT22. A resolução digital é 0,25 °C; isso não equivale à precisão ou calibração.

| Situação | Novos campos | Dashboard |
| --- | --- | --- |
| Leitura válida | `probe_ok: true`, temperatura numérica (inclusive zero) | Temperatura da sonda em °C |
| Falha / termopar aberto | `probe_ok: false`, temperatura null | Falha na leitura |
| Firmware antigo | Ambos omitidos no POST; ambos null na resposta | Sem leitura da sonda |

Campos enviados pela metade, combinações inconsistentes, NaN e infinitos são rejeitados com 422. Uma leitura antiga continua marcada como desatualizada. Não há histórico ou inferência de IA nesta integração.

## Verificação física pendente

Com API e frontend ligados, observe a sonda em repouso, aqueça levemente a ponta com a mão, acompanhe a mudança e aguarde a estabilização. Confirme os campos pelo GET e o card no dashboard. Confira também falha apenas na sonda e falha apenas no DHT22, respeitando as ligações e desligando a alimentação antes de alterar a montagem.

Uma leitura numérica isolada não comprova montagem correta, calibração ou precisão. O teste físico não foi realizado nesta alteração.

Verificação de software realizada: 46 testes da API passaram, o build com checagem TypeScript passou e oito cenários de renderização com dados simulados passaram (leitura válida, zero, falha da sonda, falha do DHT22, campos omitidos, campos null na resposta, dados antigos e API inacessível). Não houve inspeção visual em navegador. Sem Arduino CLI disponível e sem a biblioteca MAX6675 instalada no ambiente, o firmware não foi compilado nem gravado nesta atividade.
